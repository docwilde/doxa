# Rust 2.0 engine adapter plan

This is a port plan for DOXA session engines, based on the Python contracts in `doxa/engines.py`, `events.py`, `engine.py`, `codex.py`, `vendors.py`, `cli_isolation.py`, `auth.py`, `transcript.py`, and `daemon.py`. It describes a target contract, not implemented Rust provider parity. LORE remains a separately installed service and store; Rust must not absorb `lore_core` or silently promise its surfaces.

## Boundary and order

1. **Freeze the session contract.** Put `Engine`, `EngineProvider`, `EngineEvent`, `EngineCapabilities`, and a registry in a Rust engine crate independent of UI and transport. Declare all 18 current capability booleans from `EngineCapabilities` with `false` defaults; bind a handle's live declaration, never infer it from engine ID. Implement lifecycle, one active turn plus bounded FIFO prompts, out-of-band events, and cancellation before choosing a provider. Preserve `None` for unknown model, cost, or context values.
2. **Port transcript and fixture harness.** Write/read DOXA's own JSONL schema, a separate provider-resume sidecar, and a deterministic fake engine. Make provider wire fixtures drive the same event assertions. This allows integration with a Rust daemon without live credentials.
3. **Codex adapter.** It has the narrowest controllable input: `codex exec --json` subprocess and stdin prompt. Port its JSONL mapper, failure detection, process-group cleanup, thread sidecar, and CLI sandbox config. Start with `mcp_tools=false` until a Rust MCP sidecar or an explicitly retained external `python -m doxa.mcpserver` is exercised end to end; advertise the latter as a Python runtime dependency if chosen.
4. **Vendor chat API adapter.** One implementation parameterized by DeepSeek and GLM specs. Port SSE and incremental tool-call argument accumulation, usage accounting, request/response limits, tool-loop bound, and credential isolation. Enable model tools only when a working gated operator bridge exists. Never treat an API balance endpoint as session cost.
5. **Claude adapter.** Decide and prove a supported boundary first: a Rust-to-Claude Agent SDK bridge process (Python dependency) or a separately validated Claude CLI protocol. The current Python engine is an in-process `claude_agent_sdk` client; its hooks, `can_use_tool`, streaming, resume, and `get_context_usage` cannot be copied by assuming ordinary `claude` CLI JSON output. Implement bridge/version handshake and fixture recording, then enable each capability only after a live compatibility test.
6. **External integrations.** Attach DOXA peer delivery and a LORE client/sidecar through explicit optional interfaces. Keep memory unavailable per session when the service or store is absent. Gate LORE tools on both `lore=true` and a functioning bridge; index the DOXA transcript on finalization only when that integration is configured. Review/derive and belief pickers need separate parity work.

## Engine API and exact normalized shapes

Use these Rust types as the initial adapter boundary (JSON shown because events also cross the daemon socket). `start() -> session_started`, `send(prompt) -> stream<Event>`, `peer_events() -> stream<Event>`, `finalize() -> session_done`, `set_model(Option<String>)`, `set_permission_mode(String)`, `answer_needs_input(id, answer) -> bool`, `context_usage() -> Option<map>`, `usage_summary()`, and peer/queue access mirror `engines.Engine`. `switch_branch` is a session operation, not a provider API request. `stop` is a daemon operation and must not be required of every engine. Belief and pending pickers are optional LORE integration methods, not `Engine` members.

```json
{"type":"turn_started","data":{"prompt":"user text","peer_context":false,"turn_id":"abc123","peer_started":false,"peer_origin":null}}
{"type":"text_delta","data":{"text":"visible text","parent_id":"optional parent tool id"}}
{"type":"reasoning_delta","data":{"text":"visible reasoning","parent_id":"optional parent tool id"}}
{"type":"tool_call","data":{"id":"call id","name":"tool name","input":{}}}
{"type":"tool_result","data":{"id":"call id","name":"tool name","result_summary":"short text","is_error":false,"duration_ms":12}}
{"type":"turn_done","data":{"duration_ms":123,"cost_usd":null,"session_cost_usd":null,"num_turns":1,"is_error":false,"ctx_percentage":null,"ctx_tokens":null,"ctx_max_tokens":null}}
{"type":"turn_refused","data":{"reason":"budget","message":"explanation","spent_usd":1.0,"ceiling_usd":1.0,"peer_started":false,"peer_origin":null,"prompt":"user text"}}
```

`session_started.data` has `session_id`, nullable `model`, and `cwd`; `session_done.data` has `indexed`, `belief_count`, `review` or `already_finalized`. The engine may emit `prompt_queued {id,text,position}`, `prompt_dequeued {id,text}`, `model_changed {model}`, `tool_disabled {name,reason}`, peer events, and `needs_input` / `needs_input_resolved` out of band. `needs_input` has `id`, `kind` (`ask_user`, `permission`, or `spawn`), `tool_name`, and kind-specific fields: `questions` for ask, `input_summary`, `title`, `display_name`, `description` for permission, and `body`, `task` for spawn. Resolution is `{id}`. Unknown event kinds must be ignored by older clients; malformed provider frames must be counted and fail a turn where the Python adapter does so. `turn_refused` is the sole terminal event for a turn that never started. A normal or failed started turn ends exactly once in `turn_done`.

The Rust wire wrapper should preserve protocol v1 until both ends negotiate another version: `hello {type:"hello",proto:1,doxa,session_id,model,effort,engine,permission_mode,bypass_armed,cwd,next_seq}`; client `attach {cursor:null|u64}`, `prompt {id,text}`, `call {id,method,params}`; server `reply {id,ok,...}` and `event {seq,turn:null|string,event:{type,data}}`. Frames are newline JSON and at most `MAX_FRAME_BYTES` (currently 64 KiB); oversized events retain their type and sequence with `{truncated:true,note:...}`. The in-memory ring holds 512 frames; replay is `seq >= cursor`, then live events without a gap. A prompt reply assigns its turn ID before any tagged event can be published. The Rust adapter itself should produce normalized events; the daemon owns ring sequencing, attach, client claims, and broadcast.

The vendor request is `{"model":...,"messages":[{"role":"system|user|assistant|tool",...}],"temperature":0.2,"thinking":...,"tools":[...],"tool_choice":"auto","stream":true,"stream_options":{"include_usage":true}}` when tools are offered; `tool` messages carry `tool_call_id` and JSON result content. DeepSeek uses `thinking.reasoning_effort`; GLM uses root `reasoning_effort`. An SSE `delta.tool_calls[]` fragment is keyed by call index/id until arguments form JSON, then the gate receives `{name, arguments}` and a `tool_result` is emitted. Preserve the provider's reported resolved model and usage independently of the requested model.

Codex MCP today starts `python -m doxa.mcpserver` with per-turn identity and `default_tools_approval_mode="approve"`. If Rust retains this path, document Python/DOXA/LORE deployment explicitly and pass only allow-listed non-secret environment values in CLI `-c` overrides, because argv is visible. Codex's own shell/edit tools stay outside DOXA `ToolGate`; its sandbox and approval policy control them. Vendor tool calls are executed by DOXA's in-process gate. Claude's SDK `can_use_tool` and DOXA operator gate are distinct decisions. `cost=false` means the provider stream does not report billed dollars; Python can still enforce a configured spend ceiling for a known model by charging a versioned price sheet from tokens. A Rust port must label that total as derived and leave unknown-price models unbounded.

Authentication is also provider-specific. Claude login/logout/probe is `claude auth login/logout/status`; Codex is `codex login/logout/login status`, run on a private PTY with a 15-minute timeout. Only approved auth URLs/device codes may be surfaced; never log token-bearing URL parameters. Vendor keys are environment-only. Claude's isolated config is `$DOXA_HOME/claude-cli`, mode 0700, with 0600 owned settings and credential copy; copy newer valid OAuth tokens without overwriting newer isolated tokens, honor explicit logout marker, and snapshot skills one-way without symlinks back into the user's directory. Do not silently fall back to the host CLI profile when provisioning fails. Codex thread IDs are stored beside the DOXA transcript; a missing ID on requested resume is a start error, not a new thread.

## Permission, cancellation, and persistence

Claude modes are `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`; `dontAsk` and launch-armed `bypassPermissions` have gated escalation on detached sockets. Preserve the existing confirmation and arming predicates in the daemon. For a Claude tool that genuinely asks, emit `needs_input` out of band and park without an arbitrary timeout. Failure to obtain an answer denies the tool; duplicate/late answers return `false`. `AskUserQuestion` answers update the input; decline is a normal denial. Spawn has its own confirmation except in `bypassPermissions`, subject to independent depth/count/rate limits. Vendor and Codex adapters must report `permission_modes=false` until their actual controls match this contract.

A cancelled turn must close its generator/stream, stop the provider request or process, reap the Codex process group (TERM then KILL if needed), and **not** start the next queued prompt. Normal success and handled failure may advance FIFO. Keep one 3600 s wall-clock deadline per turn; Codex drains bounded stderr concurrently and enforces JSONL line/body limits; vendor SSE enforces line/body caps and the 24-step limit. Pre-turn budget refusal occurs before persistence, queue drain, request, or subprocess spawn. No cancelled or refused turn is charged as a completed turn. Detaching a client does not cancel a daemon-owned turn; daemon shutdown does.

Persist DOXA conversation JSONL independently of provider history: `{"type":"user","message":{"content":"prompt"}}`, `{"type":"assistant","message":{"content":[{"type":"text","text":"..."},{"type":"tool_use","id":"...","name":"...","input":{}}]}}`, and `{"type":"user","message":{"content":[{"type":"tool_result","tool_use_id":"...","content":"...","is_error":false}]}}`. Tool results from Claude server tools also take the final user-role shape. A user string opens a turn; a user array does not. The reader returns the latest 40 turns by default, with counts for dropped turns, capped text (20,000 chars) and tools (30); it must surface truncation rather than pretend completeness. Limit reads to 8 MiB/20,000 lines. Never persist an injected LORE snapshot as user text. Vendor messages and Codex thread state are separate files; provider resume and DOXA transcript restore are distinct claims.

## LORE as an external integration

Define an optional `MemoryBridge` with `snapshot(cwd)`, `index_transcript(path)`, `belief_count()`, and a separately capability-gated operator/picker API. No Rust code should import, migrate, or rewrite `lore_core` storage as part of the engine port. Claude currently appends a snapshot to its system prompt and refreshes through hooks; vendor sessions rebuild a system message each turn; Codex prepends a labeled snapshot once on the first stdin prompt. Preserve these provenance labels and ensure `lore=false` performs no store read and advertises no `lore_*` tools. If unavailable, the session runs without memory and its status says so. LORE write tools stage pending proposals for review; do not turn `lore_remember` into a direct store write. Belief pickers, review/derive, and context-breakdown parity are explicit follow-on gates.

## Fixtures and release gates

Keep fixtures under `rust/.../tests/fixtures/engines/` with scrubbed Python-recorded input and expected normalized events. Minimum sets: Claude SDK stream/text/thinking/tool/parent/result, permission approve/deny/disconnect and resume; Codex first turn/resume, each tool item kind, updates, unknown event, malformed JSON, nonzero exit, timeout and process-tree reap; vendor fragmented SSE/tool args, usage, two consecutive tool steps, 401/429/terminal vendor code, missing key, timeout, cancellation and GLM/DeepSeek effort bodies. Add fixture cases for budget refusal, queue order/cancel, transcript restore/truncation, isolated credential newer/invalid/logout behavior, and daemon replay/turn tagging. Secrets in fixture input and error output must be scrubbed.

Parity is **per capability and provider**, checked against the Python fixtures and live smoke runs on pinned CLI/SDK versions. Gate an advertised capability only when: (1) a deterministic fixture asserts its input-to-event mapping and failure behavior, (2) its cancellation/permission path is exercised, and (3) a live credentialed test confirms the provider still offers the observed surface. Record tested versions and date in the implementation PR. CI can test parsers and fake transports without accounts; credentialed smoke tests remain an explicit release gate. Passing a shared `Engine` interface alone does not establish provider parity.
